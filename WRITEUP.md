# Handsfree: write-up

I built Handsfree, a native Mac app that lets someone who cannot use their hands run their computer by speaking goals. It is for people with a spinal cord injury, ALS, cerebral palsy or severe RSI. Sending one email with Voice Control takes about eight commands ("Open Mail", "Show numbers", "Click 14"), each said exactly right. A booking or a form takes dozens.

Voice is the right interface here because for these users a keyboard is not slower, it is impossible. Speech runs at roughly 150 words a minute, eye-gaze typing at 10 to 20. The task also needs a conversation: the agent has to ask "Priya Shah or Priya Patel?", and the user needs a spoken "stop" that works instantly, because it is the only brake they can reach.

Here is one task from start to finish. The user says "Hey Handsfree, WhatsApp Mum: running late, ten minutes." The app wakes, and the voice agent hands the goal to the screen agent. If memory says Mum is Amma on WhatsApp, it does not ask. The real pointer opens WhatsApp through Spotlight, clicks the message box and types the line. Before it presses Send, code reads the name of the control under the pointer, `button "Send" in WhatsApp`, and the agent says, "Send 'running late, ten minutes' to Amma?" Only a spoken "yes" lets the click land. If the user says "no, say fifteen minutes", the task survives and the message changes. I ran the first half of this on a real Mac from the command line, with a test contact; it drafted the message and stopped at the held send in 17 seconds. The full spoken run through the built app is not done yet.

What makes it different is that it acts rather than points. Voice Control is one command per click, so it is a keyboard made of speech. Computer-use agents take a typed goal and expect you to walk away. Clicky, the Mac companion I built on, sees your screen and points at the button, but it needs a key held down and leaves the clicking to you. The shell of my app is adapted from Clicky's open-source code,. What makes it hands-free is new: background tasks that can ask questions, a stop that freezes the pointer mid-move, a safety check on the real button, and memory. I chose a wake phrase over an open microphone so no audio leaves the laptop while it sleeps.

I learned three things. First, the agent has to be visible: because it uses the real pointer in the user's own apps, they can trust it and stop it. The cost is speed, several seconds a step. Second, unit tests were not enough. Every package passed its tests, yet the safety check could be bypassed because three packages described a Send button in three different wordings. Only a test across packages found it, and the fix was to judge a structured action, not a sentence. Third, an agent that presses keys for someone else must refuse some windows: after a test accidentally approved a Java update, I made password prompts, installers and updaters off limits.

With more time, I would test with real users, starting with disability organisations. I would run my own voice pipeline so Jev routes each sentence before any language model, which would make "scroll down" faster, and so it can decide when a slow speaker has finished. I would add per-user speech adaptation and a speaker check, since a wake phrase does not stop a television.
