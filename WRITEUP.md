# Handsfree: write-up

I built Handsfree, a native Mac app that lets someone who cannot use their hands run their computer by speaking goals. It is for people with a spinal cord injury, ALS, cerebral palsy or severe RSI. One email with macOS Voice Control takes about eight commands ("Open Mail", "Show numbers", "Click 14"); a form takes dozens.

Voice is the right interface here because for these users a keyboard is not slower, it is impossible. Speech runs at roughly 150 words a minute, eye-gaze typing at 10 to 20. The task also needs a conversation: the agent has to ask "Priya Shah or Priya Patel?", and a spoken "stop" must work instantly, because it is their only brake.

The user says "Hey Handsfree, WhatsApp Mum: running late, ten minutes." The app wakes, and the voice agent hands the goal to the screen agent. If memory says Mum is Amma on WhatsApp, it does not ask. The real pointer opens WhatsApp through Spotlight, clicks the message box and types the line. Before it presses Send, code reads the name of the control under the pointer, `button "Send" in WhatsApp`, and the agent says, "Send 'running late, ten minutes' to Amma?" Only a spoken "yes" lets the click land. I ran the first half on a real Mac from the command line, with a test contact: it drafted the message and stopped at the held send in 17 seconds. A full spoken run through the built app is not done yet.

What makes it different is that it acts rather than points. Voice Control is a keyboard made of speech: one command per click. Clicky, the Mac companion I built on, sees your screen and points at the button, but it needs a key held down and leaves the clicking to you. The shell of my app is adapted from Clicky's open-source code,. What makes it hands-free is new: background tasks that can ask questions, a stop that freezes the pointer mid-move, a safety check on the real button, and memory. The app sleeps and listens on the Mac itself for the phrase, so no audio leaves the laptop and no conversation minutes are used until it hears it. I have tested that only with synthetic voices.

I learned three things. First, the agent has to be visible: because it uses the real pointer, the user can trust it and stop it. The cost is several seconds a step. Second, unit tests were not enough. Every package passed its tests, yet the safety check could be bypassed because three packages described a Send button in three different wordings. Only a test across packages found it, and the fix was to judge a structured action, not a sentence. It happened again when ElevenLabs silently rejected the voice agent's tool list: each part passed its tests, the join failed, and in my first spoken run the agent could only change the volume. The app now checks the agent and refuses to wake if it does not match. Third, an agent that presses keys for someone else must refuse some windows: after a test accidentally approved a Java update, I made password prompts, installers and updaters off limits.

With more time, I would test with real users, with real voices for the wake phrase. I would run my own voice pipeline so Jev routes each sentence first, making "scroll down" faster and judging when a slow speaker has finished. I would add per-user speech adaptation and a speaker check, since once a conversation is open, a television or a passer-by could still give a command.
